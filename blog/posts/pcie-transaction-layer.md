事务层(Transaction Layer)是 PCIe 离软件最近的一层:CPU 的每一次读、写、配置访问,都要在这里被翻译成一个标准化的数据包——**TLP(Transaction Layer Packet)**。

这篇文章拆解 TLP:它长什么样、有哪些类型、路由怎么决策,以及一个和操作系统紧密相关的铁律(4KB 边界)。

## 为什么需要 TLP

PCI 时代,各种控制信号、中断、电源管理都走**单独的物理线**;到了 PCIe,一切信息——数据、控制、错误报告、中断——**统一打包成 TLP**。

统一带来的好处是巨大的:物理层只需要认识一种"包"的格式,链路层只需要保护一种"包"的完整,而软件面对的唯一接口就是"收发 TLP"。协议演进(比如中断从 INTx 变成 MSI/MSI-X)不再需要新增物理信号,只是换一种 TLP 类型而已。

## 分离事务:总线效率的关键

先看一个概念:PCIe 的事务是**分离的(split)**。

请求者(Requestor)发出读请求后,**立即释放链路**;响应(完成包 Completion)由完成者(Completer)在之后作为**独立的事务**发回。

对比 PCI 时代的做法:读请求发出后,总线被占用直到数据返回——期间其他设备只能用"等待"打发时间。分离事务把"等结果"的时间还给了总线,这是 PCIe 效率大幅提升的原因之一。

## TLP 的结构

一个 TLP 由最多四个部分组成:

```
┌──────────┬──────────┬──────────────┬─────────────┐
│ Prefix   │ Header   │ Data Payload │ TLP Digest  │
│ (可选)    │ (必须)    │ (可选)        │ (可选)       │
└──────────┴──────────┴──────────────┴─────────────┘
```

- **Prefix**:可选前缀,扩展 TLP 语义用的;
- **Header(包头)**:必须存在,定义类型、目标和属性。长度是 **3DW 或 4DW**(DW = 32bit,即 12 或 16 字节);
- **Data Payload**:数据载荷,读写数据就装在这里;
- **TLP Digest**:可选摘要,做端到端的完整性检查(与链路层的 LCRC 不同,它是整条路径的)。

Header 的第一个 DW 里有几个关键字段:

- **Fmt[2:0]**:格式——包头是 3DW 还是 4DW,有没有数据载荷;
- **Type[4:0]**:类型——是内存、IO、配置还是消息事务;
- **TC(Traffic Class)**:流量等级,用来区分优先级,保证关键数据能插队先走。

### 解码表

| Fmt[2:0] | 含义 | Type[4:0] | 事务示例 |
| --- | --- | --- | --- |
| 000b | 3DW 头,无数据 | 00000 | 内存读(32bit 地址) |
| 001b | 4DW 头,无数据 | 00000 | 内存读(64bit 地址) |
| 010b | 3DW 头,有数据 | 00000 | 内存写(32bit 地址) |
| 011b | 4DW 头,有数据 | 00000 | 内存写(64bit 地址) |
| 010b | 3DW 头,有数据 | 01010 | 带数据的完成包 |
| 10xxx | (可变) | 10xxx | 消息 |

其中 `Type=00000` 代表内存操作——绝大多数数据传输都属于这一类。

## posted 与 non-posted:两种寄信方式

PCIe 事务分成两大类,用寄信来类比最直观:

### posted(投递事务):寄平信

发出去就当他送到了——**fire and forget**。

典型代表:**内存写**。"我把数据发给你,我相信你肯定能收到"——至于接收方到底怎么处理,发送方不再过问,也没有回执。

### non-posted(非投递事务):寄挂号信

寄出去了心里还得惦记着,**必须等对方签收**才算完事。

典型代表:**内存读、配置访问**。PCIe 中这个"收据"就是一个叫 **Completion(完成包)** 的 TLP。比如读内存:请求者发出读请求 TLP,必须等完成者把数据装进完成包发回来,这次读事务才算结束。

### 为什么要有这种区分

- 写操作可以"不信赖"(丢了重写一遍就行),用 posted 省去回执,总线效率更高;
- 读操作**必须**拿到数据,没有回执就无法继续,所以必须 non-posted。

这个区分贯穿驱动开发的始终:比如 DMA 完成后读状态寄存器,如果状态寄存器读不到预期值,先想想你的读事务是不是被"半路"处理了。

## 4KB 边界规则:软硬件协同设计的经典案例

PCIe 中有一条"铁律":**单个内存请求 TLP 的地址范围,绝对禁止跨越 4KB 地址边界**。

为什么定这条规则?因为操作系统的内存管理基本按"页"进行,而一页通常是 **4KB**。这条规则保证了:

> 硬件发出的任何一次请求,都不会"脚踏两只船"——同时跨越两个内存页。

万一请求跨页了会怎样?这两个页在物理内存里可能离得十万八千里,接收端(内存控制器或 DMA 引擎)就得同时处理两块不连续的物理区域,复杂度急剧上升。

所以 PCIe 硬件主动配合软件,把请求限制在单页内。**这是硬件为软件降低复杂度的教科书级设计**——也是面试官爱问"软硬件协同"时希望听到的答案之一。

## 配置请求:type0 与 type1

配置空间访问通过配置请求 TLP 完成,分两种:

- **Type0 请求**("本地访问"):发给**直连设备**。含义:"这个包是给你的。"
- **Type1 请求**("远程访问"):由 RC 或交换机发往**下游**。含义:"请将此包转发给你管辖范围内的设备。"

典型流程:根联合体(RC)发起配置访问时先发 Type1;交换机从上游收到 Type1 后,开始"找设备"——如果目标设备在自己管辖范围内,就把 Type1 请求"翻译"成 Type0 请求,直接递给那个设备。就像一封写有详细地址的信,邮局(交换机)负责转成最终能投递的形式。

## 路由决策:给 TLP 指路

一个 TLP 在链路里怎么找到目的地?按类型分三种路由方式:

1. **识别 TLP 类型**:是内存、配置还是消息包?这决定了用哪种路由方法;
2. **地址路由(Address Routing)**:对内存/IO TLP,检查目标地址是否落在某个下游端口的分配范围内;
3. **ID 路由(ID Routing)**:对配置/完成 TLP,根据 BDF(Bus/Device/Function)ID 找到正确路径;
4. **隐式路由(Implicit Routing)**:对消息 TLP,遵循特殊规则,比如"路由到根"或"向所有端口广播"。

交换机在中间扮演的角色就是:**查表 → 决定往哪个端口转**。这也是为什么 PCIe 拓扑里交换机是天然的"路由节点"。

## 小结

- **TLP 是 PCIe 的通用语言**:数据、控制、错误、中断全部统一打包;
- **分离事务**让总线在等待期间也能被其他设备使用;
- **posted/non-posted** 对应"平信/挂号信",读必须有回执(Completion),写可以不管;
- **4KB 边界规则**是硬件为操作系统"页管理"让路的经典设计;
- 路由靠 **地址 / ID / 隐式** 三种方式,交换机负责查表转发。

事务层的知识在驱动开发中最实用——特别是 posted/non-posted 的语义和 4KB 边界,直接决定 DMA 缓冲怎么分配、寄存器怎么访问。
