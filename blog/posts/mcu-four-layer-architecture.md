单片机程序写多了会有一个共同感受:裸机时代"功能全写在 main 里"的写法,一旦项目超过两三万行、功能超过三四个模块,就开始失控——改一个传感器驱动,要连带改 UI;换一个 RTOS,全工程 API 跟着遭殃。

这篇聊一套被验证过很多次的工程结构:**四层架构**。它不是某个大厂的专利,而是一组朴素的分层思想,从 BSP 到 APP,每层只做一件事。

## 四层架构长什么样

```
┌─────────────────────────────────┐
│  APP 应用逻辑层                   │  业务流程:几行代码拼出功能
├─────────────────────────────────┤
│  Service 业务组件层               │  独立组件:日志/传感器/低功耗/FOTA
├─────────────────────────────────┤
│  OSAL 系统抽象层                  │  屏蔽 RTOS/裸机差异
├─────────────────────────────────┤
│  BSP 驱动层                      │  封装底层硬件
└─────────────────────────────────┘
```

### BSP 驱动层:封装底层硬件

**屏蔽硬件差异**,向上层提供统一接口。

- 同一颗传感器芯片,不同板子的引脚可能不同——BSP 把"引脚、时序、寄存器"全部收进这一层;
- 换板子、换芯片,只改 BSP,上层的业务代码一行不动。

一个判断标准:**BSP 之上的代码里,不应该直接出现寄存器操作**。

### OSAL 系统抽象层:让 RTOS 可替换

OSAL(OS Abstraction Layer)**不直接调用 FreeRTOS 的 API**,而是包一层薄薄的封装:

```c
/* OSAL 提供的统一接口 */
osal_task_t  osal_task_create(osal_task_func_t fn, ...);
osal_mutex_t osal_mutex_create(void);
osal_err_t   osal_mutex_lock(osal_mutex_t m, uint32_t timeout);
```

好处是立竿见影的:

- 今天用 FreeRTOS,明天换 RT-Thread、uC/OS,或者**干脆回到裸机**——只改 OSAL 这一层的实现;
- 业务代码不 import 任何 RTOS 的头文件,可读性、可移植性都更好。

### Service 业务组件层:把功能拆成独立模块

把产品功能拆分为**互相独立的组件**:

- 日志模块、传感器数据处理模块、低功耗管理模块、FOTA 升级模块……

每个 Service 组件满足:

- **单一职责**:一个组件只干一件事;
- **无横向依赖**:组件之间不直接调用,只通过下面要讲的消息总线通信;
- **可单独测试**:喂入数据,验证输出。

### APP 应用逻辑层:拼业务流程

APP 层**不关心具体的驱动实现**,只管调用 Service 层的 API,几行代码拼出业务流程:

```c
void app_ble_connect_event(void) {
    service_log_record("ble", "connected");
    service_sensor_start();          // 启动采集
    service_lpm_disable();           // 退出低功耗
    service_status_set(STATUS_ACTIVE);
}
```

这一层足够薄,业务逻辑的变化(流程调整、新增场景)大多只改这里。

## 数据流与状态机:两层关键实践

分层是骨架,数据流和状态机是血肉。

### 干掉全局变量,建立消息总线

多模块协作最大的敌人是**全局变量**。两个模块直接读同一个全局变量,耦合立刻出现,而且调试时"谁改了这个值"根本查不到。

做法:**建立统一的消息总线**。

- 无论是传感器数据还是 UI 指令,统一打包成标准 Message;
- 通过**订阅/发布模式**分发,模块之间完全解耦;

```c
typedef struct {
    uint32_t     id;       /* 消息 ID */
    const void  *data;     /* 数据指针 */
    uint16_t     len;      /* 数据长度 */
    uint32_t     src;      /* 来源模块 */
    uint32_t     ts;       /* 时间戳 */
} osal_msg_t;

/* 发布:任何模块都能发 */
msg_bus_publish(MSG_SENSOR_DATA, &sample, sizeof(sample));

/* 订阅:消费方注册回调 */
msg_bus_subscribe(MSG_SENSOR_DATA, app_on_sensor_data);
```

- 不用 `if-else` 的嵌套逻辑,改用 **RTOS 的任务优先级 + 信号量**,或者**事件驱动的状态机**;
- 参数统一管理、统一读写、统一校验,任何模块拿到的参数都走同一道门。

### 状态机:替代 if-else 深渊

业务逻辑一旦复杂,`if (state && event && flag)` 的嵌套会变得不可维护。事件驱动的状态机是更可靠的替代:

```
(空闲) --上电--> (初始化) --完成--> (运行) --传感器异常--> (故障)
  (运行) --低电量--> (低功耗) --充电完成--> (运行)
  (故障) --复位--> (初始化)
```

状态机的好处:

- **状态和事件是显式的**,逻辑变成一张可读的表;
- **每个状态的处理独立成函数**,好测试、好加日志;
- 状态转移非法时能立刻被发现(断言),而不是悄悄错下去。

## 高可用与鲁棒性设计

架构是结构的,鲁棒性是行为的。两层设计值得内置:

### 全生命周期异常捕获

出现故障时,第一时间把 **CPU 现场、堆栈信息、日志存入 Flash**,之后通过 Flash 里的日志还原现场、排查故障。

嵌入式设备很多在产线/现场,没有调试器,异常落盘是"事后还原现场"的唯一手段。Cortex-M 的 HardFault handler 里做现场抓取,是这个思路的标准实现。

### 防呆与参数校验

**所有 API 接口入口都要有 Assert 判空和范围检查**:

```c
err_t service_sensor_set_threshold(uint16_t value) {
    OSAL_ASSERT(value >= SENSOR_MIN && value <= SENSOR_MAX);
    ...
}
```

入口把关,错误在上游暴露,而不是在下游以"诡异现象"的方式爆出来——这能把大量定位时间省下来。

## 小结

- **四层架构**:BSP(硬件)→ OSAL(系统)→ Service(组件)→ APP(业务),每层只依赖下一层;
- **消息总线 + 状态机**:干掉全局变量,用事件驱动代替 if-else 嵌套;
- **异常落盘 + 入口校验**:让故障可还原,让错误早暴露。

这套结构同样适用于裸机工程——OSAL 层可以退化为"直接调用硬件定时器+软件定时器",消息总线用环形队列实现,四层的骨架依然成立。规模小的时候,从 BSP/Service/APP 三层起步即可,OSAL 等真要上 RTOS 的那天再加,也不迟。
