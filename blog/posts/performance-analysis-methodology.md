"程序有点慢"是需求,不是问题。"慢在哪、慢多少、为什么"才是问题。性能优化的第一原则是:**先测量,再优化**。没有数据支撑的优化叫猜,有了数据叫工程。

这篇文章整理一套性能分析工具箱:从最朴素的计时,到 CPU 分析器、火焰图、内存分析,再到嵌入式场景下的特殊手段。

## 计时:最朴素也最容易被忽视

在怀疑"这段代码慢"之前,先把它**量**出来。

```bash
$ time ./your_program
real    0m2.561s
user    0m0.015s
sys     0m0.012s
```

`time` 输出的三个数字要能看懂:

| 时间 | 含义 |
| --- | --- |
| real(真实时间) | 从开始到结束流逝的真实时间,包含其他进程、IO 等待、阻塞 |
| user(用户时间) | CPU 执行你的用户态代码的时间 |
| sys(系统时间) | CPU 执行内核代码(系统调用)的时间 |

**通常 user + sys 才是你的程序真正消耗的 CPU**,real 远大于 user+sys 意味着程序在"等"——等 IO、等锁、等网络,而不是在"算"。这两种慢是完全不同的病:

- CPU 密集(user+sys 高):优化算法、减少计算;
- IO/等待密集(real 高、CPU 低):异步化、缓冲、减少阻塞。

> 计时也可能会骗人:机器同时跑着别的进程,或者你的程序恰好发生了等待。多次测量取中位数,比单次结果可信。

## CPU 分析器:追踪器 vs 采样器

计时要手动埋点,适合粗粒度;想知道"函数级别的耗时分布",需要分析器(profiler)。CPU 分析器分两类:

**追踪分析器(Tracing Profiler)**
记录程序的**每一次函数调用**,包括调用关系、耗时。信息最全,但开销巨大——记录本身就严重拖慢程序,甚至改变行为(Heisenberg 效应)。适合短小、确定性的代码。

**采样分析器(Sampling Profiler)**
**周期性地**查看程序当前在执行什么,记录堆栈。开销小得多,可以分析真实运行中的大程序。缺点是统计性:短函数可能采样不到,结果有概率误差。

| | 追踪器 | 采样器 |
| --- | --- | --- |
| 记录粒度 | 每一次调用 | 周期性快照 |
| 开销 | 大(可改变行为) | 小 |
| 适用 | 短代码、确定性分析 | 长运行、真实场景 |

Linux 下的事实标准是 **perf**:

```bash
# 采样 10 秒,记录调用栈
perf record -g -F 99 ./your_program
# 交互式查看
perf report
```

`-F 99` 是采样频率(每秒 99 次),`-g` 记录调用栈。99 而不是 100 是有意的:避免和程序自身的周期行为共振,产生采样偏差。

## 火焰图:让耗时分布一目了然

perf report 的文本输出信息量大但难读。**火焰图(Flame Graph)**把调用栈可视化:

```
                    ┌──────────┐
      ┌─────────────┤ func_B   ├──────────────┐
      │             └──────────┘              │
┌─────┴─────┐  ┌───────────────┐   ┌─────────┴───────┐
│ func_A    │  │ func_D        │   │ func_E          │
└───────────┘  └───────────────┘   └─────────────────┘
```

- Y 轴是调用栈深度,每个方块是一个函数,方块宽度 = 该函数占用的时间比例;
- X 轴是时间,但**不表示执行顺序**,只表示占比;
- 顶部"平顶"越宽,说明热点越集中。

生成火焰图的经典流程:

```bash
perf record -g -F 99 ./program
perf script > out.perf
# 用 FlameGraph 工具包(Ferguson/Brendan Gregg)
./stackcollapse-perf.pl out.perf > out.folded
./flamegraph.pl out.folded > flame.svg
```

> 数据可视化对性能分析不是锦上添花:分析器输出的原始数据量巨大,人眼读文本堆栈非常低效,火焰图一眼就能看出"时间都去哪了"。

## 内存分析:泄漏与越界

C/C++ 的内存错误(泄漏、越界、use-after-free)是性能与稳定的隐形杀手——内存慢慢耗尽,程序越来越慢,最后崩掉。**Valgrind** 是这里的主角:

```bash
valgrind --leak-check=full ./your_program
```

它能检测:

- 内存泄漏(分配了没释放);
- 非法读写(越界访问、读未初始化内存);
- use-after-free(释放后继续使用)。

代价是运行速度慢 10-50 倍,所以一般在测试/调试环境跑,不用于线上。

## 资源监控:先看"缺不缺"

很多时候程序变慢不是因为代码差,而是**资源不够了**:内存不足开始交换、磁盘 IO 饱和、CPU 被别的进程抢走。所以性能分析的第一步,往往是看系统资源:

- 通用:`top` / `htop`(CPU、内存、负载);
- 内存:`free -m`(物理内存 vs swap);
- IO:`iostat`(磁盘吞吐与等待)、`vmstat`(阻塞的进程数);
- 网络:`netstat` / `ss`(连接数、丢包)。

嵌入式场景的"资源监控"有自己的形态:RTOS 的任务栈水位、CPU 占用率统计(Idle 钩子)、堆内存碎片率——对应桌面端的 top/free,只是入口在调试器或日志里。

## 嵌入式性能分析的变体

桌面的 perf 在单片机/裸机上不一定能用,但有对应的手段:

| 桌面 | 嵌入式对应物 |
| --- | --- |
| perf 采样 | RTOS 任务统计(CPU 占用)、调试器采样(如 Ozone) |
| 火焰图 | 任务状态日志 + 脚本分析 |
| Valgrind | 内存池统计、栈水位检测、调试器内存检查 |
| time | 示波器/逻辑分析仪测 GPIO 翻转间隔 |
| 代码级计时 | `DWT->CYCCNT`(Cortex-M 周期计数器)、`HAL_GetTick` |

嵌入式一个实用技巧:**GPIO 翻转测时序**。在怀疑的代码段前后翻转一个 GPIO,示波器上一眼看出实际耗时、抖动、最坏情况——比任何软件计时都可信,因为它不受调试器断点影响。

另一个常用工具是 Cortex-M 的 **DWT_CYCCNT**:CPU 周期计数器,一条指令读出来,测量精度到时钟周期:

```c
volatile uint32_t t0 = DWT->CYCCNT;
/* 被测代码 */
uint32_t elapsed_cycles = DWT->CYCCNT - t0;
```

## 优化的完整流程

```
1. 测量    → 确认瓶颈在哪(计时 / 分析器 / 火焰图)
2. 假设    → 基于数据提出"慢的原因"
3. 修改    → 只改一处
4. 复测    → 同样的测量方法对比 before/after
5. 保留数据 → 优化记录:改了什么、效果多少、为什么
```

两条纪律:

- **一次只改一处**:同时改三处,即使变快了,你也不知道是谁的功劳;
- **优化后必须有数据**:没有对比数据的优化等于没优化——而且可能引入了隐蔽的复杂度。

## 小结

- **先测量再优化**,没有数据不讨论性能;
- 看懂 `real / user / sys`:CPU 密集和 IO 等待是两种病,用药不同;
- 追踪器看细节、采样器看全貌,Linux 用 `perf` + 火焰图;
- 内存问题交给 Valgrind,资源问题先看系统监控;
- 嵌入式用 GPIO 翻转、DWT_CYCCNT、RTOS 任务统计,原理与桌面完全一致。

> "过早的优化是万恶之源"——但"从不测量就谈优化"同样是。测量是成本最低的优化手段,永远排在第一位。
